# 技能1 任务建模

## 目的
回答“为什么需要发文、由谁向谁行文、要对方做什么”。用户写“报告”，实质可能是请求批准；用户只说“发个通知”，可能缺发文主体和受文范围。任务契约是后续所有判断的起点，必须由人确认。

## 输入
- 办文需求原文（如“写一份向主管部门申请示范点建设经费的报告”）；
- 可选提示：主送机关、发文机关类型、指定文种、事项编号；
- 已准入材料的结构化副本（只读）。

## 输出（TaskSpec）
每个关键字段都是“槽位”：值 + 状态（已确认 / 推断 / 未知）+ 来源。缺口（gaps）单列并标明是否需要问用户。
`forbidden_fill` 默认包含：发文字号、成文日期、签发人、审批结论、印发日期、份号、印章——这些只能来自真实办理流程。

## 执行要点
1. 目的识别（请求批准 / 汇报情况 / 部署工作 / 告知事项 / 商洽 / 答复 / 记录议定事项……）用确定性线索词，模型只做补充且须在原文中找到依据。
2. 字面文种与实质用途冲突时，给出建议而不擅自改：如“报告”中含请求批准事项 → 提示“更适合请示”（条例第十五条：报告不得夹带请示事项）。
3. 行文方向按隶属关系判断；无法判断时标“待核实”，不猜测。
4. 适用时点默认当天；用户要求按历史时点办理时改为 historical 模式。

## 必须由人完成
任务契约确认（审核节点“任务契约确认”）：确认、修改后确认、先补材料或终止。模型通道不能代为确认。

## 如何调用
- MCP：`task_create` → `material_add` → `task_advance`，然后把 `human_actions` 原样转告用户；
- 命令行：`gongwen task new "<需求>" --to <主送> --issuer <发文机关类型>`；
- 人工确认：`gongwen task confirm <任务> <节点> accept|edit --data '{"genre": "请示"}'`。

## 验收检查
- 未知字段保持未知，没有用常见值“补全”；
- 字面文种与实质用途冲突已提示；
- 禁止补写字段未出现在任何建议值中。

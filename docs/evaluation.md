# 评测

> 不能只让大模型给作文打分（设计第九章）。

## 一、运行

```bash
gongwen eval                                   # 完整系统，55 个回归用例
gongwen eval --ablate all --baselines          # 逐项消融 + minimal 基线
gongwen eval --direct                          # 加“模型直接写作”基线（须在配置中设置模型）
gongwen eval --export-review                   # 导出隐藏系统名称的盲评稿与评分表
gongwen eval --cases my_cases/ --out report/   # 自定义用例目录与输出目录
```

输出：`report.md`（总览、分组、消融、未通过用例）、`summary.json`、`results.json`（逐条期望的核对结果与指标），以及可选的 `blind_review/`。

## 二、用例

用例为 YAML（`src/gongwen/eval/cases/`），每例标注两类分组：

- **风险维度**：文种与行文、事实与依据、语义与修订、格式与版式；
- **设计 §9.2 任务组**：高频单文稿、多材料和跨文件、时间与政策适用、不完整、冲突与对抗。

五类用例：

| 类型 | 做什么 | 期望示例 |
|---|---|---|
| `pipeline` | 走完整流程，模拟人在各审核节点的处理（`accept` 自动接受、`human` 脚本） | `stage`、`genre`、`draft_contains`、`draft_not_contains`、`section_contains`、`numbers_sourced`、`authority_codes`、`conflicts` |
| `check` | 对外部文稿做规范检查 | `rules_present`（埋入的问题须检出）、`max_issues`（干净对照不得误报） |
| `admission` | 材料准入 | `admission`（逐份判定）、`finding_codes` |
| `revision` | 形成文稿后人工改写或变更关键事实 | `rules_present`、`errors_contain`、`attachment_table_contains` |
| `model` | 用脚本化模型模拟虚构、越权、拒答 | `draft_not_contains`、`log_events` |

当前 55 例的任务组构成：高频单文稿 31、多材料和跨文件 7、时间与政策适用 5、不完整、冲突与对抗 12。干净对照 3 例（用于度量误报）。

## 三、指标与设计 §9.4 的对应

| 设计维度 | 本评测指标 | 说明 |
|---|---|---|
| 文种与行文适配 | `genre`、`authority_codes`、`alternatives_include` 期望 | 文种正确、关系与权限问题检出 |
| 事实可靠性 | 无来源数字句占比；虚构数字；内容泄漏（不应出现的表述）；事实状态升级检出 | 虚构数字 = 文稿中出现、需求与材料中都没有、也不是复算或人工更正结果的数字 |
| 依据质量 | 旧规、库外文件、程序规范作实体依据、引用格式 | FB-09～11、FB-13 |
| 任务完整性 | `draft_contains`、`section_contains` | 例如通知不得漏掉材料中的任务 |
| 数字与附件 | 合计复算、附件说明与附件、交叉引用、事实变更联动 | FB-04、FB-12、FL-04、FL-05、SR-01 |
| 语义保持 | 拟议→已完成、写入未批准事项、讨论→决定 | SR-02、SR-03、GR-14 |
| 版式质量 | 要素格式检查；版式参数回读 | FL-* |
| 运行安全 | 准入判定；人工送审是否被自动通过；模型越权输出被拦截 | FB-06～08、SR-06～08 |
| 工作效率 | **未覆盖** | 须真实试点记录“达到可接受送审稿的总用时” |

消融定位到的模块贡献（关闭后由通过变为失败）：

- 事实账本：材料间数据冲突（FB-03）、人工改写造成的事实状态升级（SR-02）；
- 时效检查：引用已停止执行的 2000 年《国家行政机关公文处理办法》（FB-09）；
- 独立审校：事实状态升级、写入未批准事项、人工修改引入的标点问题（SR-02～04）；
- 定向修订：机械性问题的自动纠正（SR-04）；
- 一致性检查：表格合计、附件说明标点、正文引用不存在的附件（FB-12、FL-04、FL-05）；
- 减负检查：新增高频报送要求（SR-11）。

## 五、如何解读

- 这些是**回归测试**：用例围绕已知风险点构造，系统在开发中针对它们修正过缺陷（见提交记录），因此 full 变体 100% 通过是“守住已知问题”的含义，不代表对未知任务的准确率；
- 合成材料不代表真实办文分布；脚本化模型只模拟特定不当输出；
- “minimal”基线是“同一流程但关闭约束模块”，不是“强模型直接写作”；后者用 `--direct` 运行，须配置真实模型，并按设计 §9.3 同时报告质量与成本；
- 普通 RAG、多角色系统等基线尚未实现。

## 六、扩充到 600 例（设计 §9.2）

| 任务组 | 目标 | 现有 | 扩充建议 |
|---|---:|---:|---|
| 高频单文稿 | 300 | 31 | 六类场景 × 不同单位类型（党政机关、医院、高校、科研院所）× 多轮修改 |
| 多材料和跨文件 | 100 | 7 | 同一事项的请示 + 实施方案 + 经费表 + 汇报摘要；口径不同的两张统计表 |
| 时间与政策适用 | 100 | 5 | 新旧版本衔接、地方细则、参照执行主体、按历史时点起草 |
| 不完整、冲突与对抗 | 100 | 12 | 缺材料时的追问与暂停、越权请求、材料中的注入指令、伪造审批 |

扩充时按事项族、时间、机构、模板来源隔离划分，不把同一事项换标题后分进不同集合；真实材料须先取得授权并按准入规则处理。

## 七、人工评测（设计 §9.5）

`--export-review` 生成：

- `blind_review/R001.md …`：隐藏系统名称的评审稿（完整方案与“直接写作”基线混排、随机编号）；
- `blind_review/评分表.csv`：稿件编号、评审人、重大/一般/轻微问题数、是否可接受为送审稿、预计修改用时；
- `blind_review/评审说明.md`：双人独立评价、第三人裁定、问题分级定义；
- `blind_review_key.csv`：编号与系统的对应关系，评审完成前不得交给评审人。

须分别报告原始生成结果、自动修订后结果与人工完成后结果；不得删除失败和拒绝任务后再计算平均效果。
